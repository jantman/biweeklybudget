# Phase 0 Research: Current-Period Per-Account Transaction Totals

**Feature**: [spec.md](./spec.md) | **Date**: 2026-09-19

The Technical Context for this feature carries no `NEEDS CLARIFICATION` markers: the
stack, storage, testing and target are all fixed by the existing project, and the change
is confined to one view function, one template block, their tests and the prose that
describes them. What follows is therefore the survey of the existing code that the design
rests on, plus the handful of shape decisions the spec left to the plan.

## Existing code survey

### Where the data comes from

`BiweeklyPayPeriod.account_sums` (`biweeklybudget/biweeklypayperiod.py:498`, built by
`_make_account_sums()` at line 631) returns, for one pay period, a dict keyed by account
id with `{'name': str, 'total': Decimal}` values. It reports only the accounts it
actually observed transactions for; an account with nothing in the period is absent
rather than zero.

This property is **not changed by this feature**. It is already per-period, and it is
already the single source of the numbers. The five-period shape lives entirely above it.

### Where the five periods are assembled

`build_account_period_sums(periods)` (`biweeklybudget/flaskapp/views/payperiods.py:61`)
takes a list of periods, reads `account_sums` from each, unions the account ids seen in
any of them, and emits one row per account with a list of per-period totals, plus a list
of per-period column totals. Its docstring explains that it supplies the zeros that
`account_sums` omits, "only the view knows which accounts are on screen".

Its sole caller is `PayPeriodView.get()` at `payperiods.py:239`, which passes
`[pp_prev, pp, pp_next, pp_following, pp_last]` and hands the two return values to the
template as `acct_period_sums` and `acct_period_totals`.

**Decision**: since the helper's only job is the cross-period assembly this feature
removes, it collapses to a per-period grouping. Confirmed by grep that nothing else in
the repository references `build_account_period_sums`, so narrowing it is safe.

### Where it is rendered

`biweeklybudget/flaskapp/templates/payperiod.html:118-151` — a `panel-default` whose
heading is the literal text "Per-Account Transaction Totals", wrapping a
`table-responsive` div around `<table class="table table-bordered" id="pp-acct-table">`.
The header row is `Account` plus five period cells, four of them links to
`/payperiod/<date>` and the current one carrying `class="info"`. The body is one row per
account plus a `<strong>Total</strong>` row. Amounts run through the `reddollars` filter
with `|safe`, which wraps negatives in `<span class="text-danger">`.

**Decision**: add `biweeklybudget/tests/unit/flaskapp/views/test_payperiods.py`,

## Shape decisions

### D1: How the transposed table carries its total

**Decision**: the grand total becomes the table's last column — a `Total` header cell and
one amount cell beneath it, to the right of the account columns.

**Rationale**: in the five-column table the totals row was the sum of the column above
it. Transposed, the sum of the row's cells naturally reads as the cell at the end of that
row. Putting it first would separate the label ordering from the reading order; putting
it in a second body row would reintroduce a row the transposition exists to remove.

**Alternatives considered**: a leading label column (`Pay Period Totals` on the left) was
rejected — with a single row there is nothing to disambiguate, and the panel heading
already names what the row is. A separate footer row was rejected for the same reason.

### D2: What happens to the current-period `info` highlight

**Decision**: dropped.

**Rationale**: it existed to pick the viewed period out of five. With one period there is
nothing to pick out, and a highlight covering the whole table conveys nothing.

### D3: Which accounts get a column

**Decision**: accounts with at least one transaction in the viewed period, ordered by
name ascending — i.e. exactly the keys of that period's `account_sums`.

**Rationale**: this is the existing rule with the union over five periods removed. It
also keeps the table as narrow as the period's activity allows, which matters more now
that account count drives width rather than height.

**Consequence**: the helper no longer needs to supply zeros for accounts absent from a
period, because the only accounts on screen are ones the period observed. The docstring
paragraph explaining the zeros goes with it. An account whose transactions net to exactly
zero still has a column, because `account_sums` still reports it.

### D4: The helper's name and signature

**Decision**: `build_account_period_sums(periods) -> (rows, column_totals)` becomes
`build_account_sums(period) -> (columns, total)`.

**Rationale**: the old name and signature both advertise the multi-period behaviour being
removed; keeping either would leave the next reader expecting a sequence. The function is
module-private in practice (one caller, same module) and appears in no public API
documented outside the autogenerated Sphinx API pages, so renaming costs nothing.

**Alternatives considered**: keeping the name and passing a one-element list was rejected
as leaving dead generality and a misleading signature behind.

### D5: Template variable names

**Decision**: `acct_period_sums`/`acct_period_totals` become `acct_sums`/`acct_total`.

**Rationale**: `acct_period_totals` was plural because it held one total per period;
there is now exactly one number, and a plural name for a scalar would mislead. Both names
are local to this one render call and this one template block.

### D6: Table identity and wrapper

**Decision**: keep `id="pp-acct-table"`, the `table table-bordered` classes, the
`table-responsive` wrapper and the panel heading text.

**Rationale**: the spec's assumptions call for it, the responsive wrapper is what handles
the new horizontal growth, and leaving the heading alone keeps the change to what the
issue asked for.

## Risks

- **Horizontal overflow with many accounts** — accepted and anticipated by the issue. The
  `table-responsive` wrapper already present makes the table scroll horizontally inside
  the panel rather than widening the page. No new mechanism is needed; the acceptance
  suite should confirm the wrapper still encloses the table.
- **Acceptance test fixtures that only differ between periods** — the existing
  `TestPayPeriodAccountTotals` fixture deliberately puts `PrevOrdinary` in the previous
  period and `NextOrdinary` in the next, to prove the non-current columns worked. Those
  transactions keep their value under the new shape as the proof that adjacent-period
  activity is *excluded*, so the fixture is retained as-is and only the assertions change.
